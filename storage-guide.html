tapo-uploader

Set up where the recordings go

The recordings can go to YouTube, to your own OneDrive, to a WebDAV cloud such as Nextcloud, to anything rclone supports, or to a folder on the server. Each destination needs a little one-time setup. Who does it depends on how the software is run:

  • Just you, one camera (single-user): you do all of it, and write the values in the .env file.
  • A server for several people (multi-account): the administrator prepares the destinations once, in the server's environment file; then each person picks one on their Recordings page. YouTube and OneDrive need an app registered by the administrator; WebDAV needs nothing from the administrator; rclone and the folder are chosen by the administrator for everybody.

YouTube

Videos go to each person's own channel as private videos, one playlist per day. Google asks for an "app" to be registered once.

Administrator (or you, single-user)

  1. Create a project at console.cloud.google.com and enable the YouTube Data API v3 for it.
  2. Open Google Auth platform (OAuth consent screen): app name, your support email, audience External. Add the Google accounts that will use it as Test users (up to 100).
  3. Open Clients → Create client.
    • Several people on a server: type Web application, authorized redirect URI https://YOUR-ADDRESS/youtube/callback. Download the JSON and put its content in YOUTUBE_CLIENT_SECRET_JSON.
    • Just you: type Desktop app, download the JSON as client_secret.json and run python tapo_uploader.py auth once.
  4. While the app stays in Testing the access expires after 7 days. Publish it ("In production"): Google then wants a home page, a privacy policy and the matching authorized domain, your own, not this project's. The README explains it step by step.

Each person

On the personal page press Connect YouTube, choose the Google account and allow the access. Videos are uploaded privately; YouTube does not play private videos inside another site, so the card offers Open the video (it opens on YouTube, where you are signed in).

Limit: Google gives 10,000 quota units a day to a project and a day's upload costs about 1,700, so a project serves around five people. The administrator page shows the day's use.

OneDrive

Each person connects their own OneDrive (personal, or work/school). The app can use only its own folder, Apps in their OneDrive, never the rest of their files. This needs an app registered once by the administrator, and a server that runs the multi-account mode.

Administrator

  1. Sign in at portal.azure.com (a free Microsoft account is enough) and open Microsoft Entra ID → App registrations → New registration.
  2. Name: tapo-uploader. Supported account types: Accounts in any organizational directory and personal Microsoft accounts.
  3. Redirect URI: platform Web, value https://YOUR-ADDRESS/storage/onedrive/callback. Register.
  4. On the overview page copy the Application (client) ID: it is MS_CLIENT_ID.
  5. Certificates & secrets → New client secret. Copy the Value (not the ID) at once, it is shown only now: it is MS_CLIENT_SECRET. It expires (up to 24 months): note the date and make a new one before it.
  6. API permissions → Add a permission → Microsoft Graph → Delegated: add Files.ReadWrite.AppFolder and offline_access (and keep User.Read). No admin consent is needed.
  7. In the server's environment file set the two values, make sure the server has PUBLIC_URL, ALLOW_OWN_STORAGE=1 and onedrive in STORAGE_ALLOWED (it is by default), then restart. 
    MS_CLIENT_ID=00000000-0000-0000-0000-000000000000
MS_CLIENT_SECRET=the-secret-value
# MS_TENANT=common     # common (default) | consumers | organizations

Each person

Recordings → Connect OneDrive, sign in with Microsoft and accept. Recordings appear in your OneDrive under Apps, in one folder per day. You can remove the access at any time in your Microsoft account (privacy, apps and services). Work or school accounts may ask an administrator to approve an app that is not publisher-verified.

The OneDrive connection has been tested against a simulation of Microsoft's service, not yet on a real account: tell us if something differs.

WebDAV (Nextcloud, ownCloud, Synology...)

The simplest one: nothing to register, everybody can use their own.

  1. Nextcloud: create an app password instead of using your login password: Settings → Security → Devices & sessions, type a name, Create new app password. It also works when two-factor is on.
  2. The address is shown in Nextcloud's Files → Settings → WebDAV. It looks like https://cloud.example.com/remote.php/dav/files/YOUR-USER. Other products have their own address (ownCloud is similar, Synology uses its WebDAV Server package).
  3. On Recordings choose WebDAV, fill address, user, password and an optional folder (for example Tapo), press Test the connection, then Save.

The address must be public and https (the password would otherwise travel in clear), and it cannot point inside the server's own network. For a server-wide WebDAV the administrator sets STORAGE=webdav, STORAGE_WEBDAV_URL, STORAGE_WEBDAV_USER, STORAGE_WEBDAV_PASSWORD, STORAGE_WEBDAV_FOLDER (single-user: STORAGE=webdav, WEBDAV_URL, WEBDAV_USER, WEBDAV_PASS, WEBDAV_FOLDER).

rclone (Mega, S3, Backblaze, Dropbox, Google Drive...)

rclone talks to dozens of storage services. It is chosen by the administrator for the whole server (a configuration chosen by a user would give access to the server itself). The Docker image already contains rclone.

  1. Install rclone on the computer where you can sign in, and run rclone config: n (new remote), give it a name such as cloud, pick the service from the list and follow the questions (for S3-compatible services: access key and secret; for Dropbox or Google Drive: a browser sign-in). Check it with rclone lsd cloud:.
  2. Copy the configuration file (rclone config file shows where it is) to the server, readable only by the user that runs the software.
  3. Set, in the server's environment file: 
    STORAGE=rclone
STORAGE_RCLONE_REMOTE=cloud
STORAGE_RCLONE_CONFIG=/data/rclone.conf     # optional: where the file is
STORAGE_RCLONE_FOLDER=Tapo                  # optional
# single-user .env: RCLONE_REMOTE, RCLONE_CONFIG, RCLONE_FOLDER

Mega works through rclone's mega backend, but the author has not tested it: Mega has no official API for this, so read rclone's documentation for its limits before relying on it. OneDrive can also be reached through rclone, but the direct connection above is easier for several people, because each one signs in on their own.

A folder on the server

Plain files in Tapo YYYY-MM-DD folders, for people who keep the footage on the machine that runs it (a NAS, a home server). Set STORAGE=local and STORAGE_LOCAL_ROOT=/path/to/videos (single-user: LOCAL_ROOT). With Docker, mount that path as a volume. Everyone sees only their own camera's subfolder and watches the videos from their page.

Changing destination later

Change it any time on Recordings. The destination used until then is kept in your list of earlier destinations: its videos stay on your page, each marked with where it lives (YouTube, OneDrive, WebDAV...). Removing an earlier destination from the list only hides it; no video is ever moved or deleted.

If something does not work

  • The page has no choice, only a notice: the administrator has not enabled personal destinations (ALLOW_OWN_STORAGE=1), or has not set up the app for that service.
  • YouTube asks to connect again every week: the Google app is still in Testing; publish it.
  • OneDrive: "Microsoft no longer accepts the saved access": connect OneDrive again (the sign-in expired, a password changed, or the client secret ran out).
  • WebDAV: login refused or "redirect": use the final https address and an app password; the test button tells you which.
  • Videos do not play in the page: keep the camera on H.264; H.265 may not play in some browsers.
